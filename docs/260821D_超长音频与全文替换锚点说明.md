# 《弦字幕》（LyraSub）当前超长音频与全文替换锚点说明

## 一、电影级超长音频：当前版本实际具备什么

当前版本可以把一个 MP3 作为单一工程导入，并由 faster-whisper 按其内部语音片段流式产出识别结果。识别任务逐片段建立词级时间戳；中文、日文、韩文等 CJK 文本再在单词时间范围内按字符近似分配。因而，即便是一部电影的音频，识别阶段的原始锚点在数据结构上仍带有完整的全局毫秒时间，而不是从零开始的分段局部时间。

| 环节 | 当前行为 | 电影级风险 |
|---|---|---|
| MP3 导入 | 一次导入一个完整文件 | 文件长会增加识别时长，但不改变全局时间轴 |
| 本地识别 | faster-whisper 逐语音片段产生锚点，界面按已处理时长显示进度，可停止 | 显存、CPU/GPU 时长与模型大小决定实际耗时 |
| LLM 清洗 | 把当前整篇文本作为**一次**请求发送 | 可能超过模型上下文、服务商输入限制或请求超时 |
| LLM 切分 | 把当前整篇文本作为**一次**请求发送，要求返回完整 JSON 字幕数组 | 长片可能造成超大 JSON、服务端生成慢或返回失败 |
| 锚点映射 | 切分后的字幕文本重新对齐完整原始锚点列表 | 算法本身可覆盖全片，但大幅改写会提高复核量 |

> 结论：**当前没有“自动把电影切成若干 LLM 块并自动汇总”的产品功能。**本地识别能处理长音频；真正需要分块的是 LLM 清洗与 LLM 语义切分。

## 二、当前可立即执行的稳妥工作流

对电影或特别长的访谈，建议先完整完成本地识别并保存工程。之后不要把整部片的文本一次交给 LLM，而是在文稿中按章节、场景或自然段拆分为多个工作段。优先在明显的场景转换、片头片尾、长音乐、长静音或叙事章节边界处拆分，而不是在一句话中间断开。

每一段的推荐流程是：保留原片工程作为母工程；复制或另存一个段落工程；仅对该段文字执行清洗与语义切分；校对黄色条目；再导出该段 SRT。最终按原始时间码把各段 SRT 汇总。由于每段仍使用来自原音频的毫秒锚点，合并后的字幕仍处在同一全片时间轴中。

| 项目规模 | 当前建议 |
|---|---|
| 0–30 分钟 | 可尝试单次 LLM 清洗和切分；超时建议保留 300 秒或按服务稳定性提高 |
| 30–120 分钟 | 建议按场景或章节分段；每段独立调用 LLM 并复核 |
| 电影级、多人对白、服务不稳定 | 不建议单次发送全文；采用章节化项目与分段 SRT 汇总 |

## 三、下一阶段可实现的自动分块方案

后续可在软件中增加“长片批处理模式”。该模式不应简单按字数硬切，而应以原始锚点时间为底座进行块规划。

| 步骤 | 自动策略 | 目的 |
|---|---|---|
| 1. 生成候选边界 | 使用长静音、识别语音片段间隔、句末标点和章节标记 | 避免切断一句对白 |
| 2. 规划时间块 | 目标每块约 10–20 分钟，限制文本字符数与预计输出量 | 控制模型上下文、响应时间和 JSON 大小 |
| 3. 加入短重叠 | 两侧保留少量上下文，但只提交中心区域的最终条目 | 防止边界处语义丢失与重复字幕 |
| 4. 分块调用 LLM | 每块独立清洗、切分、校验和可重试 | 一个服务错误不会损坏整部电影 |
| 5. 全局汇总 | 使用原始毫秒锚点排序、去除重叠区重复条目、运行时间围栏校验 | 保持全片单一、连续的时间轴 |
| 6. 断点续作 | 每完成一个块即写入工程草稿和块状态 | 可从失败块继续，而非重新处理全片 |

这是推荐的下一阶段开发方向；它尚未进入当前 v260821D 的用户界面。

## 四、整段覆盖粘贴外部修改文本：原始锚点到底会怎样

在“清洗后的文本”框中按 `Ctrl+A` 并粘贴外部修改稿，**不会立即删除、移动或修改原始识别锚点**。原始锚点独立保存在工程中，包含识别词/字符、开始毫秒、结束毫秒和识别来源片段。点击“确认清洗文本”时，软件只记录新的清洗文本；真正的重新对齐在随后执行“自然语义切分”、离线切分或表格重新映射时发生。

重新对齐采用顺序匹配，而不是按字符位置硬套：原始锚点序列与新文本被拆为可见单元后进行序列比对。CJK 按单字比对；英文等空格语言按词比对。换行被当作字幕边界而不是新发声单位。

| 外部覆盖后的文本情况 | 锚点处理 | 校对状态 |
|---|---|---|
| 大部分文字相同，只纠错、删口头语、调整标点和换行 | 相同的词/字重新链接到原有锚点 | 通常为“已继承” |
| 新文字位于两段仍匹配的原文中间 | 仅在两侧均有可靠锚点时，按中间空档分配**估算**时间 | 黄色：需复核：估算时间 |
| 新文字位于全文开头/结尾，或周边原文也被大改 | 不制造假时间 | 黄色：需复核：缺少锚点 |
| 完全替换为另一份措辞差异极大的稿件 | 仍相同的零散字词可能被顺序匹配；其余部分不会可靠继承 | 大量黄色；应人工复核或手工定时 |

原始锚点不会“错乱”，因为算法不原地重写它们；它只为新的字幕条目建立新的锚点引用或新建带风险状态的辅助锚点。需要注意的是：当文本改写幅度很大、出现大量常见词或多次重复句子时，纯文本顺序匹配在语义上可能不如人工判断可靠。因此，黄色条目必须试听复核；即使显示“已继承”，在剧本完全重写的情形下也应抽样检查。

## 五、覆盖外部文本时的安全建议

首先保存工程，保留原始识别文本作为可回退层。若外部文稿只是校订，尽量保持对白顺序与主要用词；处理完立即运行语义切分，观察黄色复核数量。若外部文稿是重写式字幕或翻译稿，不应期待自动继承原语种每个字的精确时间：更合适的做法是以原锚点为粗定位，在校对页试听并手工调整关键段落的起止时间；音乐、静音和新增说明文字可使用“插入字幕”建立人工定时条目。

> 核心原则：**锚点层永远保留，字幕层可以重建；系统宁可标黄要求复核，也不把不可靠的对齐伪装成精确时间。**
